Demanda

Visitas, tasa ATC y conversión a orden

SELECT_PRODUCT, SELECT_ADD_TO_CART (Amplitude, departmentName IN ('Moda mujer','Moda hombre')) y Órdenes (marketplace_products_pa) — dos tasas distintas, no las confundas (ver nota abajo)

Tasa ATC = engagement (SELECT_ADD_TO_CART ÷ Visitas) — cuánta gente agrega al carrito. Tasa de conversión a orden = compra real (Órdenes ÷ Visitas) — a pedido de Heidy ("solo estamos viendo add to carts, necesito conversion rate"). Son números muy distintos en magnitud (la conversión a orden es casi siempre menor que la tasa ATC, porque no todo lo que se agrega al carrito se compra) — no se deben promediar ni comparar directamente entre sí.

Queries de referencia (copiar/pegar en Databricks)

Guardadas acá para que un refresh futuro parta del query real en vez de reconstruirlo de memoria. Réplica exacta de la metodología del dashboard de Beauty y Salud, con el filtro de categoría cambiado a Moda.

GMV / Órdenes / AOV / Compradores / Aliados con venta — Moda (día)
SELECT CAST(p.origination_date_local AS DATE) AS d,
       SUM(p.gmv_cop) AS gmv_cop, SUM(p.gmv_usd) AS gmv_usd,
       COUNT(DISTINCT p.order_id) AS orders, COUNT(DISTINCT p.client_id) AS buyers,
       COUNT(DISTINCT p.suborder_ally_slug) AS allies_selling
FROM addi_prod.sandbox.marketplace_products_pa p
JOIN addi_prod.gold_ds.f_catalog_taxonomy_current_co t ON t.sku_id = p.sku_id
WHERE t.l1 = 'Moda'
  AND CAST(p.origination_date_local AS DATE) BETWEEN :desde AND :hasta
GROUP BY 1 ORDER BY 1
GMV total Marketplace (día) — mismo scope que arriba, SIN el join de taxonomía
SELECT CAST(origination_date_local AS DATE) AS d,
       SUM(gmv_cop) AS gmv_cop_mp, COUNT(DISTINCT order_id) AS orders_mp
FROM addi_prod.sandbox.marketplace_products_pa
WHERE CAST(origination_date_local AS DATE) BETWEEN :desde AND :hasta
GROUP BY 1 ORDER BY 1
Nuevos compradores Moda / Nuevos MP → Moda (día)
WITH cat_first AS (
  SELECT p.client_id, MIN(CAST(p.origination_date_local AS DATE)) AS first_cat_date
  FROM addi_prod.sandbox.marketplace_products_pa p
  JOIN addi_prod.gold_ds.f_catalog_taxonomy_current_co t ON t.sku_id = p.sku_id
  WHERE t.l1 = 'Moda'
  GROUP BY 1
),
mp_first AS (
  SELECT client_id, MIN(CAST(origination_date_local AS DATE)) AS first_mp_date
  FROM addi_prod.sandbox.marketplace_products_pa
  GROUP BY 1
)
SELECT cf.first_cat_date AS d,
       COUNT(DISTINCT cf.client_id) AS new_buyers_cat,
       COUNT(DISTINCT CASE WHEN mf.first_mp_date = cf.first_cat_date THEN cf.client_id END) AS new_mp_to_cat
FROM cat_first cf JOIN mp_first mf ON mf.client_id = cf.client_id
WHERE cf.first_cat_date BETWEEN :desde AND :hasta
GROUP BY 1 ORDER BY 1
Cancelaciones r28 (día) — a nivel ALIADO (ally_category), no SKU
SELECT CAST(origination_date_local AS DATE) AS d,
       COUNT(*) AS suborders_cat,
       SUM(CASE WHEN days_between_origination_and_cancellation IS NOT NULL
                 AND days_between_origination_and_cancellation <= 28 THEN 1 ELSE 0 END) AS cancel_r28
FROM addi_prod.gold_product.dm_originations_marketplace_master_table_by_suborder
WHERE ally_category IN ('Moda','Zapatos','Joyas y accesorios')
  AND CAST(origination_date_local AS DATE) BETWEEN :desde AND :hasta
GROUP BY 1 ORDER BY 1

Take rate / Fee y contribución (semana) — aplicaciones con ≥1 suborden Moda, ally_category
WITH cat_apps AS (
  SELECT DISTINCT application_id
  FROM addi_prod.gold_product.dm_originations_marketplace_master_table_by_suborder
  WHERE ally_category IN ('Moda','Zapatos','Joyas y accesorios')
)
SELECT date_trunc('week', CAST(c.origination_date_local AS DATE)) AS wk,
       SUM(c.gmv_usd) AS gmv_usd, SUM(c.mdf_amount_usd) AS mdf_usd,
       SUM(c.lead_gen_fee_amount_usd) AS lead_gen_usd,
       SUM(c.synthetic_origination_marketplace_purchase_fee_amount_usd) AS mpf_usd,
       SUM(c.contribution_income_usd) AS contribution_income_usd
FROM addi_prod.gold.dm_contribution_income_components_co c
JOIN cat_apps ca ON ca.application_id = c.application_id
WHERE CAST(c.origination_date_local AS DATE) >= :desde
GROUP BY 1 ORDER BY 1
Tipo de crédito (semana) — crudo, SIN reescalar (reescalar en runtime al GMV real de la semana)
SELECT date_trunc('week', CAST(origination_date_local AS DATE)) AS wk,
       SUM(CASE WHEN application_synthetic_product_category='INTRO' THEN suborder_total_amount ELSE 0 END) AS intro_cop,
       SUM(CASE WHEN application_synthetic_product_category='CUPO' THEN suborder_total_amount ELSE 0 END) AS cupo_cop,
       SUM(CASE WHEN application_synthetic_product_category='GRANDE' THEN suborder_total_amount ELSE 0 END) AS grande_cop,
       SUM(CASE WHEN application_synthetic_product_category NOT IN ('INTRO','CUPO','GRANDE')
                 OR application_synthetic_product_category IS NULL THEN suborder_total_amount ELSE 0 END) AS otro_cop
FROM addi_prod.gold.dm_originations_marketplace_suborders_co
WHERE suborder_ally_category IN ('Moda','Zapatos','Joyas y accesorios')
  AND (application_synthetic_product_category IS NULL OR application_synthetic_product_category != 'MISSING_LOAN_PROPOSAL_PRODUCTV2')
  AND CAST(origination_date_local AS DATE) >= :desde
GROUP BY 1 ORDER BY 1

Envío gratis y LBA — % de subórdenes (semana) — el join correcto, para no re-descubrirlo
-- Bridge crítico: master_table.suborder_id (formato "1619363921024-01") NO es la misma suborder_id
-- de suborders_co (ese campo ahí es un UUID interno, otro namespace -- un join directo da 0 filas).
-- El campo correcto es suborders_co.suborder_vtex_external_id_array[0], que sí matchea el formato de
-- master_table.suborder_id Y el de f_marketplace_orders_shipments_co.sub_order_id.
WITH cat AS (
  SELECT m.suborder_id, date_trunc('week', CAST(m.origination_date_local AS DATE)) AS wk
  FROM addi_prod.gold_product.dm_originations_marketplace_master_table_by_suborder m
  WHERE m.ally_category IN ('Moda','Zapatos','Joyas y accesorios')
    AND CAST(m.origination_date_local AS DATE) BETWEEN :desde AND :hasta
),
enriched AS (
  SELECT c.wk, s.suborder_shipping_amount, s.suborder_vtex_external_id_array[0] AS ext_id
  FROM cat c
  JOIN addi_prod.gold.dm_originations_marketplace_suborders_co s
    ON s.suborder_vtex_external_id_array[0] = c.suborder_id
)
SELECT e.wk,
       COUNT(*) AS total,
       SUM(CASE WHEN e.suborder_shipping_amount = 0 THEN 1 ELSE 0 END) AS free_shipping_n,
       SUM(CASE WHEN sh.sub_order_id IS NOT NULL THEN 1 ELSE 0 END) AS lba_n,
       SUM(CASE WHEN e.suborder_shipping_amount = 0 AND sh.sub_order_id IS NOT NULL THEN 1 ELSE 0 END) AS free_and_lba_n
FROM enriched e
LEFT JOIN addi_prod.silver.f_marketplace_orders_shipments_co sh ON sh.sub_order_id = e.ext_id
GROUP BY e.wk ORDER BY e.wk

Supuestos y aproximaciones conocidas

⚠️
Definición de categoría Moda: las métricas a nivel SKU (GMV, órdenes, compradores, L2/L3) usan f_catalog_taxonomy_current_co.l1 = 'Moda'. Las métricas a nivel ALIADO (Cancelaciones, Take rate/Fee, Tipo de crédito, Envío gratis/LBA, cluster) usan ally_category IN ('Moda','Zapatos','Joyas y accesorios') — tres categorías de aliado agrupadas porque la tabla canónica de aliados no tiene un único valor "Moda" y porque Zapatos/Joyas son categorías de aliado estrechamente relacionadas con Moda en la operación de Addi. Un aliado clasificado en alguna de esas tres que vendiera algo fuera de Moda (ej. un aliado "Zapatos" que también vende ropa de otra l1) quedaría incluido igual en esas métricas — se espera que sea un efecto marginal dado que la mayoría de estos aliados son mono-categoría. Esta es la misma mecánica de discrepancia SKU-vs-ALIADO ya documentada en el dashboard de Beauty (ahí: 'Belleza','Salud').
⚠️
Vista mensual, métricas de conteo distinto (Buyers, Aliados con venta): al agregar desde series semanales, se usa el promedio de las semanas del mes, no la suma — sumar conteos de entidades distintas entre semanas sobre-cuenta a quienes repiten compra/venta en más de una semana del mismo mes.
⚠️
Histórico diario limitado: las series diarias (GMV/Órdenes/Buyers/Aliados con venta/Cancelaciones/GMV-Órdenes Marketplace total/Nuevos compradores/Listings/Tipo de crédito/Fee/Envío gratis/Amplitude) cubren desde el 2 de julio de 2026 (~116 días) — no hay un año completo de dato diario. Por eso el YoY de las tarjetas iniciales se calcula contra la serie semanal (58 semanas desde 2025-09-01, semana actual vs. la semana equivalente hace 364 días), no contra un día específico de hace un año.
⚠️
Meta de GMV — reparto no lineal y meta mensual, AJUSTADO 2026-10-19 (ver sección "Meta" arriba): el factor día-de-semana (DOW_WEIGHT) sigue viniendo del GMV real de Moda jul-oct 2026 (sin cambio, es la base de datos más amplia y reciente que hay). Los multiplicadores de ventana de campaña (Hot Sale, Black Friday + Cyber Monday, Navidad, BF_RAMP) ya NO se reutilizan de Beauty: se recalcularon desde el GMV real DIARIO de Moda en oct-dic 2025 (baseline = promedio Moda 1-15 oct 2025, cada ventana = promedio real de Moda en esas fechas 2025 ÷ baseline). Moda resultó con lifts más fuertes que Beauty en casi todas las ventanas (ej. Black Friday+Cyber 2.96x vs 2.27x de Beauty) y con un comportamiento opuesto en Navidad-foco (Moda SÍ tiene lift, 1.67x; Beauty cae a 0.73x ahí). La meta mensual también se recalculó: ya no es el input de negocio original (estimaba un share creciente de Moda de 6.75%→8.50% dentro del Marketplace); ahora es (share real reciente de Moda, 6.04% — promedio ponderado de las últimas 8 semanas en Databricks) × (meta de GMV del Marketplace completo: Oct $61,710M / Nov $78,460M / Dic $78,980M COP, dada por Heidy), lo que da una meta de Moda más baja que la original ($3,727M/$4,739M/$4,770M COP vs. los $4,936.5M/$6,584.6M/$7,543.9M anteriores). Dos supuestos para validar con Heidy: (1) el método de ventana-vs-baseline no separa crecimiento orgánico de fin de año del efecto puro de campaña, así que parte de esos multiplicadores puede ser tendencia normal de temporada, no solo campaña; (2) el share 6.04% es un promedio plano de 8 semanas sin tendencia — si Moda está ganando o perdiendo peso dentro del Marketplace de forma sostenida, un share fijo lo subestimaría o sobreestimaría hacia diciembre.

Inventario — SKUs y productos en catálogo / vendibles por semana, por aliado (Change 6, corregido 2026-10-27), adaptada de la query de referencia dada por Heidy (27 aliados de T2_ALLIES, granularidad Semanal, + JOIN a taxonomía Moda)
WITH periods AS (
  SELECT s.ally_slug, s.sku_id,
    COALESCE(CAST(s.product_id AS STRING), CONCAT('sku_', s.sku_id)) AS prod_key,
    s.start_date,
    CASE WHEN s.current_record_flag THEN NULL ELSE s.end_date END AS end_date,
    CAST(s.item_availability = 'available' AND s.product_id_is_active AND s.product_id_is_visible AS INT) AS vendible
  FROM addi_prod.gold_product.dm_marketplace_sku_stock_period s
  JOIN addi_prod.gold_ds.f_catalog_taxonomy_current_co t ON t.sku_id = s.sku_id
  WHERE s.ally_slug IN (/* 27 aliados de T2_ALLIES */) AND t.l1 = 'Moda' AND s.start_date <= DATE'2026-10-26'
),
deltas AS (
  SELECT ally_slug, prod_key, start_date AS d, 1 AS d_total, vendible AS d_vend FROM periods
  UNION ALL
  SELECT ally_slug, prod_key, end_date, -1, -vendible FROM periods WHERE end_date IS NOT NULL AND end_date <= DATE'2026-10-26'
),
sku_day AS (SELECT ally_slug, d, SUM(d_total) AS d_sku_total, SUM(d_vend) AS d_sku_vend FROM deltas GROUP BY ally_slug, d),
prod_day AS (SELECT ally_slug, prod_key, d, SUM(d_total) AS d_total, SUM(d_vend) AS d_vend FROM deltas GROUP BY ally_slug, prod_key, d),
prod_run AS (
  SELECT ally_slug, prod_key, d,
    SUM(d_total) OVER (PARTITION BY ally_slug, prod_key ORDER BY d) AS run_total,
    SUM(d_vend) OVER (PARTITION BY ally_slug, prod_key ORDER BY d) AS run_vend
  FROM prod_day
),
prod_flag AS (
  SELECT ally_slug, prod_key, d,
    CAST(run_total > 0 AS INT) AS in_total, CAST(run_vend > 0 AS INT) AS in_vend,
    LAG(CAST(run_total > 0 AS INT), 1, 0) OVER (PARTITION BY ally_slug, prod_key ORDER BY d) AS prev_total,
    LAG(CAST(run_vend > 0 AS INT), 1, 0) OVER (PARTITION BY ally_slug, prod_key ORDER BY d) AS prev_vend
  FROM prod_run
),
prod_delta AS (SELECT ally_slug, d, SUM(in_total - prev_total) AS d_prod_total, SUM(in_vend - prev_vend) AS d_prod_vend FROM prod_flag GROUP BY ally_slug, d),
calendar AS (
  SELECT a.ally_slug, c.d FROM (SELECT DISTINCT ally_slug FROM periods) a
  CROSS JOIN (SELECT explode(sequence(date '2026-01-28', date '2026-10-26', interval 1 day)) AS d) c
),
daily AS (
  SELECT c.ally_slug, c.d AS fecha,
    SUM(COALESCE(s.d_sku_total, 0)) OVER w AS skus_en_tabla,
    SUM(COALESCE(s.d_sku_vend, 0)) OVER w AS skus_vendibles,
    SUM(COALESCE(p.d_prod_total, 0)) OVER w AS productos_en_tabla,
    SUM(COALESCE(p.d_prod_vend, 0)) OVER w AS productos_vendibles
  FROM calendar c
    LEFT JOIN sku_day s ON s.ally_slug = c.ally_slug AND s.d = c.d
    LEFT JOIN prod_delta p ON p.ally_slug = c.ally_slug AND p.d = c.d
  WINDOW w AS (PARTITION BY c.ally_slug ORDER BY c.d)
),
filtered AS (SELECT * FROM daily WHERE fecha >= date '2026-06-24')
SELECT ally_slug, fecha, skus_en_tabla, skus_vendibles, productos_en_tabla, productos_vendibles
FROM filtered
WHERE (dayofweek(fecha) = 2 OR fecha = date '2026-10-26')
ORDER BY ally_slug, fecha
Query original de Heidy colapsaba los 27 aliados en un solo total semanal (SUM(...) GROUP BY fecha, sin ally_slug) — se adaptó dejando ally_slug en el SELECT final para tener el detalle por aliado (Ally Deep-Dive) y luego sumar en JS para el total de categoría (Category Summary), en vez de correr la query dos veces. También se cambió el corte de domingo (dayofweek(fecha)=1 en la versión original de Heidy) a lunes (dayofweek(fecha)=2, corregido 2026-10-27 a pedido de Heidy) para que coincida con el spine de T2_WEEKS/T2_CATALOG_LOG_WEEKLY del resto de esta pestaña, y se fijó el corte al día maduro 2026-10-26 en vez de current_date() (evita desfases de zona horaria del servidor).
